# Архитектура Telegram News Bot

Документ для тех, кто собирается править код. Здесь — поток данных одного
прогона, что делает каждый модуль и почему именно так, где живут компромиссы
и где код намеренно простой.

## Цели

- Автоматически публиковать в Telegram-канал по одной интересной новости в час из 6 тематических категорий и сводку мировых новостей дважды в сутки.
- Использовать только бесплатные API без карты и подписки.
- Работать без своего сервера — запуск по расписанию, состояние между прогонами хранится в git.

## Не-цели

- **Не** хранить архив постов в репозитории. Архив — сам канал в Telegram.
- **Не** извлекать полный текст всех записей RSS подряд. Стоит дорого по сети, для выбора достаточно сниппета.
- **Не** платить за API. Внешние сервисы можно заменить, но бесплатность — жёсткое требование.
- **Не** работать как long-running сервис. Бот — это один скрипт, который делает проход и завершается.

           │       │                          │     ├── LLM-выбор 5 тем (1 запрос, llm.py)
           │       │                          │     └── add_news × N (пометить URL)
           │       │                          ├── assets/digest_cover.jpg    ← обложка

           │
           ├──► main.py:26 _publish_entry()           ← полный пайплайн одной статьи
           │       │
           │       ├── extractor.py:34 get_article()  ← trafilatura + og:image
           │       ├── ai.py:72 process_article()     ← перевод + суммаризация (1 запрос)
           │       ├── main.py:53-58 цепочка картинки (og → RSS → Pexels → Pollinations)

Главная точка входа — `main.py:123 run()`. Файл `main.py:26 _publish_entry`
проводит одну статью через весь пайплайн, `main.py:90 _publish_digest` —
альтернативная ветка для дайджестов.

## Модули

### `feeds.py` — RSS-обвязка
- `feeds.py:5 get_entries` — обёртка над `feedparser`. Падающая лента
  возвращает `[]`, остальные продолжают обрабатываться (`feeds.py:14`).
- `feeds.py:21 entry_image` — достаёт URL картинки из разных полей RSS
  (`media_content`, `media_thumbnail`, `links`). Разные ленты кладут картинку
  в разные места.

### `extractor.py` — извлечение текста статьи
- `extractor.py:34 get_article` — качает страницу через `trafilatura.fetch_url`
  и возвращает `(текст[:4000], og:image)`. Текст обрезается на 4 000 символов
  (`extractor.py:9 MAX_CHARS`) — укладывается в контекст free-модели и
  экономит токены.
- Один HTTP-запрос на статью, og:image парсится из того же HTML — без
  второго сетевого раунда.
- `extractor.py:21 _extract_og_image` прогоняет URL через `html.unescape`:
  в HTML амперсанды экранированы, и раньше URL вида `...?w=1600&amp;h=900`
  уходил в `requests` как есть — CDN отвечал 400, и og:image молча терялась
  (поймано на images.ctfassets.net 26.09.2026).

### `ai.py` — перевод + суммаризация
- `ai.py:72 process_article` — один запрос к OpenRouter возвращает четыре поля:
  русский заголовок, выжимку, теги, описание картинки на английском.
- Промпт `ai.py:23 PROMPT` требует **только русский** для полей
  «Заголовок/Текст/Теги» и только английский для «Картинка» — `ai.py:15 SYSTEM_PROMPT`
  повторяет это дважды, потому что на практике одного упоминания для
  некоторых MoE-моделей мало.
- Парсинг ответа — `ai.py:47 RESPONSE_RE`. Терпим к мусору: `\s*` вместо
  `\n+\s*` между полями (модель иногда пишет всё в одну строку), и `Карт\S*`
  вместо `Картинка` (на живых прогонах модель один раз отдала слово с
  латинскими буквами на конце).
- `ai.py:62 split_into_paragraphs` — группирует выжимку по 2 предложения.
  Модель не умеет делать абзацы стабильно, поэтому форматируем сами.
- **Деградация ответа — пропуск, не публикация.** `ai.py:108-115` отбраковывает
  ответ, не попавший в regex. Раньше здесь публиковался сырой `content`,
  и в канал проскочил мусор с `<unk>`-ами.
- Сам вызов LLM — через `llm.chat_completion` (`ai.py:90`): перебор моделей,
  `reasoning: {enabled: False}` и логирование ответов без `choices` живут
  в одном месте для всех трёх потребителей.

### `selector.py` — выбор самой интересной статьи
- `selector.py:35 select_best` — собирает список `(url, title, snippet)`,
  перемешивает (`selector.py:45`) и одним запросом просит модель вернуть
  **только номер** от 1 до N.
- Перемешивание важно: free-модели склонны к position bias и тяготеют к
  первому пункту списка.
- `selector.py:60` — парсинг числа через `\d+` с проверкой диапазона
  (`selector.py:66`). Вне диапазона → `selector.py:67` warning + `return ''`,
  и `main.py` уйдёт в обычный round-robin.

### `digest.py` — сводка мировых новостей
- `digest.py:93 build_digest` — собирает до `DIGEST_CANDIDATES` сниппетов из
  `WORLD_FEEDS` (`config.py:70`) и одним запросом просит модель выбрать
  `DIGEST_TOPICS` тем **из разных областей** (политика, экономика, технологии…).
- `digest.py:73 _parse_bullets` — принимает и тире `—`, и дефис `-` (модель
  пишет по-разному), строки без разделителя отбрасывает как мусор.
- Если модель дала меньше `DIGEST_MIN_TOPICS` тем — `digest.py:139-142`
  возвращает `''`, и `main.py:143` уходит в обычный прогон, чтобы не
  публиковать обрубок.
- URL успешно использованных кандидатов помечаются сразу после сборки
  (`digest.py:145-147`), чтобы следующий дайджест не повторял
  одно и то же.

### `llm.py` — общая точка входа в OpenRouter
- `llm.py:15 chat_completion` — один ответ модели для всех трёх
  потребителей (`ai.process_article`, `selector.select_best`,
  `digest.build_digest`). До 26.09.2026 каждый модуль строил запрос сам, и
  в трёх местах повторялись одни и те же грабли.
- Модели перебираются по `OPENROUTER_MODELS` (`config.py:16`): основная,
  затем запасная. Это лечит два регулярных режима отказа free-пулов:
  429/5xx (через `retry.post_with_retry`) и HTTP 200 **без поля `choices`**
  с ошибкой провайдера в теле — раньше такой ответ падал в
  `KeyError: 'choices'`, тело нигде не логировалось, и дайджест 26.09.2026
  пропал «без причины». Теперь тело логируется (`str(body)[:300]`) и
  запрос уходит к следующей модели.
- `reasoning: {enabled: False}` (`llm.py:52`) — критично для reasoning-моделей:
  без флага они тратят весь `max_tokens` на рассуждения вслух и обрезаются,
  не успев дать ответ.
- Пустая строка означает «не ответила ни одна модель»: вызывающий код
  пропускает статью, в канал мусор не уходит.

### `image_gen.py`, `pexels.py` — источники картинки
- `image_gen.py:16 generate_image_url` — собирает URL для
  [Pollinations.ai](https://image.pollinations.ai) с параметрами
  `width=1024&height=576&nologo=true`. Без ключа, без карты. Анонимный
  Pollinations больше 1024x576 не отдаёт и игнорирует больший запрос
  (проверено 26.09.2026), поэтому эти картинки проходят только через
  «последний шанс» в `images.fetch_image`.
- `pexels.py:9 search_photo` — ищет одно стоковое фото по промпту на
  английском, отдаёт `large2x` (1880x1253). Раньше отдавал `large` (940x529),
  который стабильно не проходил `MIN_IMAGE_LONG_SIDE` и сжигал кандидата.
- Обе функции возвращают `''` при ошибке — вызывающий код просто идёт
  дальше по цепочке.

### `images.py` — скачивание картинки
- `images.py:10 download_image` — `stream=True` + `iter_content` + лимит
  `MAX_IMAGE_BYTES` (`config.py:80`). Без лимита вредоносный URL из RSS
  мог бы исчерпать память раннера.
- `images.py:30` — отбраковка по `content-type`. Если URL вернул HTML
  вместо картинки (типичная ситуация для битых og:image), сразу идём дальше.
- `images.py:87 fetch_image` — линейная цепочка: первый кандидат, прошедший
  порог `MIN_IMAGE_LONG_SIDE` (1080px), побеждает. Если выше порога не прошёл
  никто, отдаёт лучшую скачанную картинку не меньше `LAST_RESORT_LONG_SIDE`
  (800px) — пропущенная новость дороже картинки чуть мягче. `None` остаётся
  только на случай «не скачалось вообще ничего», и `main.py:59` обязан его
  проверять: 26.09.2026 распаковка `None` как кортежа уронила два прогона
  подряд.

### `publisher.py` — Telegram Bot API
- `publisher.py:74 post_news` — отправляет фото через `sendPhoto` (multipart,
  байты), при ошибке откатывается на `sendMessage` (`publisher.py:99`).
  Пост не теряется, если картинку не получилось доставить.
- `publisher.py:12 _ok` — проверка `response.json()['ok']`. `raise_for_status`
  ловит HTTP-ошибки, но Bot API на бизнес-ошибку (битый HTML, неверный
  `chat_id`) отвечает HTTP 200 с `ok: false`. Без этой проверки отправка
  считалась бы успешной, хотя ничего не ушло.
- `publisher.py:47 _build_caption` — HTML вместо Markdown, потому что
  `html.escape` экранирует одной функцией; ручное экранирование Markdown
  легко забыть в одном из двух мест отправки. Обрезка выжимки по лимиту
  делается **до** экранирования, иначе можно перерезать `<a href="…` пополам
  и получить 400 «Unclosed start tag» от Telegram.
- `publisher.py:20 _normalize_tags` — публикуется только тег категории
  источника (`#ИИ`, `#Наука`). Теги от модели не передаются: они нестабильны
  и превращаются в визуальный шум без пользы для навигации.

### `database.py` — память бота
- `database.py:18-20` — `data/seen_urls.txt` (URL опубликованных статей) +
  `data/state.json` (сервисные значения: курсор round-robin). Текстовые
  файлы вместо SQLite (`news.db`): рантайму нужны только два факта,
  бинарник в git создавал коммит на каждый пост и не diff'ился.
- `database.py:47 _save_state` — атомарная запись через `tempfile` + `os.replace`.
  Без атомарности падение процесса посреди `write_text` обрезало бы `state.json`
  до хвоста, а параллельный прогон (cron + ручной) мог бы прочитать
  полузаписанный файл.
- `database.py:90 add_news` — добавляет URL **только после успешной отправки**.
  Иначе упавшая публикация помечала бы статью как вышедшую, и она
  навсегда терялась — никогда не ретраилась. Цена — редкий дубль, если
  процесс упадёт между отправкой и меткой, но дубль заметно лучше тихой
  потери новости.

### `retry.py` — устойчивость к 429/5xx
- `retry.py:6 post_with_retry` — POST с экспоненциальной паузой (2с → 4с → 8с)
  на временные сбои: 429, 5xx, сетевые. 4xx кроме 429 не ретраим — это уже
  ошибка в самом запросе, повторять бесполезно.
- Единственный потребитель — `llm.chat_completion` (`llm.py:44`), то есть
  три LLM-вызова из одного места. У Pexels ретраев нет: ошибка там просто
  сжигает кандидата картинки и цепочка идёт дальше.

### `config.py` — настройки
- `config.py:100 FEEDS` — словарь категория → `[(имя, URL), ...]`. Round-robin
  и селектор обходят его плоский список (`main.py:158-164`), добавлять
  источник = добавить кортеж. Список собирается чередованием по категориям
  (первые источники всех категорий, затем вторые и т.д.), а не блоками: иначе
  окно из `CANDIDATES_PER_RUN` подряд идущих источников могло целиком лечь в
  одну категорию и несколько прогонов подряд выдавали одну тему.
- `config.py:70 WORLD_FEEDS` — мировые ленты для дайджеста.
- `config.py:55 DIGEST_HOURS_UTC` — часы (UTC), в которые main переключается
  в режим дайджеста. Сейчас это 05:00 UTC = 08:00 по Минску (один дайджест
  в сутки).
- `config.py:31-41` — квоты, завязанные на бесплатный лимит OpenRouter
  (~50 RPD). 4 прогона × 2 LLM-запроса (selector + process_article) —
  3 обычных поста, + 1 дайджест = ~7 RPD, с запасом.

## Память бота

- **Что хранится:** только два факта — «этот URL уже постили» и «где сейчас
  курсор round-robin». Заголовки, выжимки, даты — не хранятся, архив постов
  это сам канал.
- **Где живёт:** `data/seen_urls.txt` (по одному URL на строку) и
  `data/state.json` (JSON со всеми сервисными значениями).
- **Атомарность:** `state.json` пишется через временный файл + `os.replace`
  (`database.py:47`). `seen_urls.txt` дописывается через `open(..., 'a')` —
  для однострочного добавления в конец атомарность гарантируется POSIX.
- **Между прогонами:** раннер GitHub Actions эфемерный, поэтому воркфлоу
  коммитит `data/` обратно в репозиторий (`.github/workflows/post_news.yml:53`).
- **Concurrency:** воркфлоу использует `concurrency.group: post-news`
  (`.github/workflows/post_news.yml:26-28`), чтобы одновременных прогонов
  не было — иначе два прогона гонялись бы за `state.json` и за `git push`.
- **Ручной запуск поверх cron** безопасен именно благодаря этому —
  параллельного исполнения быть не может.

## LLM-стратегия

Бот бьёт по OpenRouter в трёх местах. Все три — `ai.py:72 process_article`,
`selector.py:35 select_best`, `digest.py:93 build_digest` — ходят через
`llm.chat_completion` (`llm.py:15`) и делят список `OPENROUTER_MODELS`
(`config.py:16`): сначала основная модель, затем запасная.

**Стоимость одной статьи: 2 запроса.** Селектор выбирает из 5 кандидатов,
суммаризатор переводит и сжимает. Дайджест — 1 запрос, без селектора.
Запасная модель тратит дополнительный запрос только при сбое основной,
так что дневной расход остаётся в пределах ~7 RPD.

**Что заставляет ломаться:**
- Reasoning-модели. Без `reasoning: {enabled: False}` они тратят весь
  `max_tokens` на рассуждения вслух и обрезаются, не успев дать ответ.
  Это поймано вживую и теперь жёстко выключено в `llm.py:52`.
- Модели «протухают». Free-пулы на OpenRouter регулярно меняются или
  возвращают 429 всем подряд. Актуальный список —
  <https://openrouter.ai/models?max_price=0>. При смене основной модели
  нужно проверять regex-парсинг ответа вживую: модель может выбрать другой
  разделитель или начать писать поля по-другому. Запасная модель — не
  замена живой проверке, а страховка от разовых сбоев.
- Ошибка провайдера под видом успеха. 26.09.2026 OpenRouter дважды ответил
  HTTP 200 без поля `choices` (в теле — `error`), и дайджест пропал: код
  падал в `KeyError: 'choices'`, тело ответа нигде не логировалось. Теперь
  `llm.chat_completion` логирует тело и пробует следующую модель.
- Модель плохо следует инструкциям. Поэтому «только русский» дублируется
  в system и в user (`ai.py:15`, `ai.py:35`), парсинг ответа терпим к
  мусору (`ai.py:47`), а обрезанные/мусорные ответы **не публикуются**
  (`ai.py:108-115`, `selector.py:60-67`, `digest.py:139-142`).

## Расписание и квоты

- **4 прогона в сутки** — в 05:00, 10:00, 15:00, 19:00 UTC (08:00, 13:00,
  18:00, 22:00 Минска). Запускается внешним будильником cron-job.org →
  `workflow_dispatch`, см. README. Встроенный GitHub `schedule` отключён: он
  не гарантирует исполнение и отбрасывает большую часть ежечасных слотов.
- **Один прогон в сутки — дайджест**, в 05:00 UTC (08:00 Минска). main.py сам
  выбирает режим через `_is_digest_hour` (`main.py:84`).
- **~7 RPD к OpenRouter** = 3 селекта + 3 суммаризации + 1 дайджест.
  Укладывается в бесплатную квоту ~50 RPD с запасом на 429-ы.
- **`MAX_ARTICLES_PER_RUN = 1`** (`config.py:31`) — намеренно один пост
  за прогон. При росте потребления (или падении квоты) крутить именно эту
  константу и количество часов в cron-job.org.

## Failure modes

| Что если | Что делает бот | Где |
| --- | --- | --- |
| Лента RSS упала | `feeds.get_entries` вернёт `[]`, остальные источники продолжат обрабатываться | `feeds.py:14` |
| `trafilatura` не смог достать текст | Статья пропускается с warning | `main.py:35` |
| og:image битый / не картинка | Цепочка идёт дальше: og → RSS → Pexels → Pollinations | `images.py:30` |
| Pexels 429 | `requests.raise_for_status` бросит исключение, `search_photo` вернёт `''` | `pexels.py:21` |
| OpenRouter 429 | `post_with_retry` сделает 3 попытки, затем `llm` перейдёт к запасной модели; если и она не ответила — статья пропускается | `retry.py:6`, `llm.py:44` |

## Что не сделано намеренно

Это **известные дыры**, не баги. Документирую, чтобы не выглядело как упущение.

- **Нет тестов.** Ни unit, ни интеграционных. Парсинг ответа LLM, цепочка
  картинки и атомарность `state.json` — самое просящееся покрытие.
- **Нет метрик и алёртов.** Единственный способ узнать о проблеме — зайти
  в логи воркфлоу. «Пост не ушёл» сейчас никем не замечается, кроме
  человека, который сам туда посмотрит.
- **Один провайдер LLM.** Вся ставка на OpenRouter free-tier. Запасная
  модель в `OPENROUTER_MODELS` спасает от сбоя конкретной модели, но не от
  исчерпания квоты или падения самого OpenRouter.
- **Нет rate-limit per-feed.** Источник, который отдаёт 100 записей в час,
  теоретически может занять весь бюджет. Сейчас его ограничивает только
  `MAX_ARTICLES_PER_FEED = 2` и общее время джобы (25 минут).
- **`data/seen_urls.txt` грузится целиком в `set()`** (`database.py:31`).
  При десятках тысяч URL работает, при сотнях тысяч начнёт лагать.
  Естественное решение — индекс по хэшу, но это уже структура данных,
  которой в боте не должно быть.
- **Нет авторизации на push `data/`** в воркфлоу. Держится на
  `permissions: contents: write` (`.github/workflows/post_news.yml:23`).
  Для публичного репо этого достаточно, для форка нужен отдельный PR.
- **Нет троттлинга на RSS.** `feeds.get_entries` ходит параллельно по
  источникам в одном цикле, последовательно — но при расширении до
  сотен лент стоит сразу заложить асинхронность или семафор.
